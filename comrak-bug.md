# comrak upstream defects

Two defects in comrak 0.54.0's inline `Sourcepos`, both still present on comrak `main` at commit 1f0db01 from 2026-08-30. Neither is filed yet. There is no fix branch yet for either; the issue bodies below are the short problem-and-cause statements.

Defect 1 has a workaround in this repo: `parse_shadow` in `crates/rune-md/src/parse/shadow.rs` expands leading tabs to spaces in the container-prefix region before the text reaches comrak. Once a comrak release carries the fix, that expansion can go. Defect 2 has no workaround, so the end column of a multi-line code span, raw HTML inline or display math that opens after its paragraph's first line is wrong on screen by the indentation difference between two lines.

comrak's README bans content generated by language models in issues, pull requests and code. These texts were produced with one. Rewriting in your own words before filing is your call.

## Issue 1: Inline sourcepos columns shift right on a lazy continuation line that starts with a tab

Inline source positions are documented as 1-based byte columns. On a lazy continuation line that starts with a tab, where a list item consumes only part of that tab, every inline node on the line reports a column 1 or 2 bytes too far right.

```
"- > x\n\tabc"    text "abc"  start column 4, should be 2
"1. > x\n\tabc"   text "abc"  start column 3, should be 2
"1. - x\n\tabc"   text "abc"  start column 3, should be 2
"- a\n\tb"        text "b"    start column 2, correct
```

The shift equals the tab width the list item left unconsumed. A consumer mapping the position back to its own buffer cannot correct for it, because a `Sourcepos` carries no record of how much of the tab a container consumed.

### Cause

`Parser::advance_offset` sets `partially_consumed_tab` and leaves the offset on the tab byte. On the lazy continuation path `Parser::add_line` then pushes the unconsumed width as literal spaces into the block's content and records the offset past the tab in `line_offsets`. `Subject::make_inline` adds the index into that content, which counts the synthetic spaces, to the recorded offset, which does not subtract them. Ordinary continuation avoids this because `add_text_to_container` advances past the whitespace with `columns = false` first, clearing the flag.

### Solution

No fix branch yet.

## Issue 2: Multi-line inline node takes its end column from the wrong line

When an inline node spans a newline and opens after its paragraph's first line, its end column is taken from the wrong line's indentation. The error is negative or positive by the indentation difference between two lines, so the reported column still lands inside the line and no bounds check catches it.

```
"a\n`\n  é`"    Code        2:1-3:3   end column should be 5
"a\n  `\né`"    Code        2:3-3:5   end column should be 3
"a\n<b\n  x>"   HtmlInline  2:1-3:2   end column should be 4
"a\n$$\n  x$$"  Math        2:1-3:3   end column should be 5
"  `\né`"       Code        1:3-2:3   correct, opens on line 1
```

### Cause

`Subject::adjust_node_newlines` indexes `parent_line_offsets` by `self.line - node_ast.sourcepos.start.line`. `parent_line_offsets` is the enclosing block's `line_offsets`, which every other reader indexes relative to the block's first line, not the inline node's. `handle_potential_attribute` has the same index with the same defect.

### Solution

No fix branch yet.
