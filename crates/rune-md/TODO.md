## Residual strict-invariants panics: comrak sourcepos self-inconsistency under lone-CR/tab + nested-container interactions

**Status:** open; found during verification round 9's adopted-reviewer-fuzz-harness sweep (≥3 passes × ~214k fresh-seed docs), AFTER fixing every producer bug this crate's own code was responsible for (see round 9's commit `fix: container-aware per-line ranges for verbatim blocks` for the full list). Reduced the panic rate from 76/214k (reviewer seeds) and 74/214k (fresh seeds) down to 18/214k and ~28/214k respectively; the remainder is a DIFFERENT, deeper bug class than anything round 9 was scoped to fix — documented here rather than silently left unexamined.

- **Root cause, confirmed via multiple independent fuzz-minimized repros:** comrak's own `Sourcepos` for two SIBLING AST nodes can report genuinely OVERLAPPING byte ranges — not a case of our own code mis-deriving a range from a reliable sourcepos, but comrak itself handing back inconsistent source positions — specifically when a lone `\r` (a line terminator comrak recognizes but the editor's own LF-only buffer model does not, per `LineIndex.comrak` vs `LineIndex.buffer`) or a raw tab character interacts with:
  - a list item's own lazy-continuation indentation requirement (tab-stop expansion appears to be applied inconsistently — once, or twice, depending on how many container levels re-derive it — when the tab sits on a continuation line inside a blockquote nested in a list item), or
  - an HTML block's (`type 7`) continue-until-blank-line matching combined with a `\r`-terminated line, where the block's own reported end extends into a byte a SIBLING top-level `Paragraph` independently claims.
- **Minimal repros (all confirmed to panic ONLY under `strict-invariants`/`cfg(test)`, and confirmed to degrade gracefully — no panic, no data loss — in an ordinary non-strict build, per this crate's documented `STRICT_INVARIANTS` design in `emit/mod.rs`):**
  - `"- >_\r\tx\n]"` (tab immediately after a lone `\r`, inside a blockquote nested in a list item, on a lazy-continuation line) — `Text("x")`'s sourcepos column comes back as if 2 extra virtual columns were inserted by tab-stop expansion, landing its byte range on top of the following `Text("]")`'s.
  - `">\t<b>\ra"` (tab right after a bare `>` blockquote marker, an HTML block, then a lone `\r`) — the `HtmlBlock` node's own sourcepos end extends past the `\r` into a byte a separate top-level `Paragraph`/`Text("a")` also claims.
  - `"- >👍\n\tx\nc"` — same list+blockquote+tab shape, no `\r` involved, confirming tab-stop expansion alone (not just the lone-CR desync) can trigger it.
- **Why this is out of scope for a `per_line_content`-style fix:** every round 9 fix (Verbatim/TextRun/EmphasisM/InlineCodeM/LinkM's `content_lines`, plus the two follow-on fixes for `InlineCodeM::open`/`close` and the wikilink lone-CR detection) corrects OUR OWN arithmetic when a single node's reliable outer sourcepos gets misapplied across a multi-line or container-prefixed range. This class is different: the sourcepos comrak hands us for two DIFFERENT nodes is already mutually inconsistent before we touch it. There is no "derive the range more carefully" fix for that — the two nodes' claims are actually contradictory at the source. A real fix would mean either (a) reconciling sibling ranges post-hoc by construction (risking silently swallowing real content at the seam, which is worse than the current graceful-degradation fallback), or (b) replicating comrak's own tab-stop/line-continuation column arithmetic well enough to predict and correct the discrepancy — both well beyond this round's scope.
- **Safety net already in place (why this is trackable, not urgent):** `assert_invariant` (`emit/mod.rs`) only panics when `STRICT_INVARIANTS` is true (`cfg(test)` or the opt-in `strict-invariants` feature). Every one of the repros above was independently re-run against an ordinary `cargo build`/`cargo run` (no `strict-invariants` feature) and printed `ok` — the existing `push_span_split_by_line`/`build_line_conversions` degrade-gracefully paths (skip an already-claimed byte / merge overlapping hidden ranges) already absorb this class in any real, shipped build. No user-facing panic or data loss risk today.
- **Next step:** either (a) file the sourcepos inconsistency upstream against `comrak` with the three minimal repros above, or (b) if it recurs at a rate that matters, build a targeted post-parse reconciliation pass that detects two sibling nodes' ranges overlapping and clips the LATER one to start where the earlier one's reliable claim ends (would need its own careful audit — do not do this as a quick patch).
